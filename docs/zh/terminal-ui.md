# 终端界面与手持形态

本文是终端**外观层**的唯一详细说明：坐标系、布局常量、配色、动画时长、首次开机引导，以及物品本体的 3D 模型与手持动画。

玩法真相不在这里。终端的页面语义、工具解锁条件与异象形态见 [异象、终端形态与个人追逐](anomalies-and-pursuits.md)；主线任务链见 [世界接口终局](world-interface.md)；协议与持久化边界见 [架构与安全边界](architecture.md)。

## 坐标系

终端在一张 512×256 的虚拟画布上绘制。`TerminalScreen#render` 先在屏幕空间贴面板底图，然后 `pushMatrix` → `translate(left, top)` → `scale(scale, scale)`，此后所有绘制都用画布坐标。缩放由 `panelScale()` 算出，钳在 `[0.55, 2.0]`。

`local(mouseX, mouseY)` 做屏幕→画布的反向换算，所有命中判定都在画布坐标里做。

### scissor 陷阱

`GuiGraphics#enableScissor` **自己会跑一遍当前 pose**。所以裁剪矩形必须传终端自己的画布坐标，绝不能预先换算成屏幕像素——那会让变换被应用两次，把整块画面裁没。

同理，裁剪框要在压入内容偏移**之前**开启，否则裁剪框会跟着内容一起偏移，滑入的内容永远裁不掉：

```java
graphics.enableScissor(body.left(), body.top(), body.right(), body.bottom());
graphics.pose().pushMatrix();
graphics.pose().translate(dx, 0.0F);
// …绘制…
graphics.pose().popMatrix();
graphics.disableScissor();   // 必须在外层 popMatrix 之前
```

vanilla 的 `ScissorStack#push` 会与父矩形求交，所以嵌套是安全的（天气工具的仪表卡片裁剪嵌在页面裁剪里）。

## 布局

全部 `Bounds` 常量在 `terminal/TerminalUiLayout`（**main 源集**，所以 JUnit 可以直接测，不需要客户端）。`TerminalUiLayoutTest` 钉住：文本与交互区必须落在 `DISPLAY` 内；硬件列必须落在 `HARDWARE_SAFE` 内且不得进 `DISPLAY`；三层结构（标签条 / `PAGE_BODY` / `STATUS_BAR`）互不相交。

| 层 | y 范围 | 内容 |
|---|---|---|
| 标签条 | 45–62 | HOME / TOOLS / RECORDS / FILES |
| `PAGE_BODY` | 70–199 | 当前页内容 |
| `STATUS_BAR` | 202–215 | 持有人 / 世界时 / 链路 / 协议号 |

硬件列（x ≥ 389，不属于 `DISPLAY`）：示波器、罗盘、调谐滑块、LCD、关闭提示。

> `FOOTER` 是 `STATUS_BAR` 的历史别名，保留只为不打断测试里按名字引用的包含列表。

状态栏那一格叫"链路"而不是"频段"：右侧硬件列已经有调谐滑块和 LCD 在讲频率，底部再写一个"频段"会让玩家以为两者是同一个数。它读的是 `bandStage`——这台设备被授权接入到第几级——与手上那个旋钮无关。

每一格都是**暗色固定标签 + 亮色自适应读数**。读数放不下时先整体缩放，缩到像素字体的可读下限仍放不下就截断加省略号；标签**永远不缩**。早先是把标签和值当一个整体缩放的，于是一个十六字符的玩家名会把"持有人"三个字一起拽小，而过了缩放下限它干脆溢出到隔壁格里。

## 不要背景板

**这个界面里的层次靠线、靠留白、靠明暗，不靠往上糊不透明色块。**

显示区已经是一整块玻璃（`GLASS_BACKDROP` 半透明压深）加 CRT 层。在它上面再填一块不透明矩形，看起来就是一张贴纸盖在设备上，而不是设备自己的屏幕——这一条是从实机观感上退回来的，开机自检、引导说明行和状态栏都曾经各自糊过一块。

现在只剩三类填充是允许的：

- **半透明的卡片底**（`CARD_BODY`）——它是页面既有的语言，且透得出下面的玻璃。
- **仪器凹槽**（示波器、罗盘、滑块、进度条轨）——那些是硬件的一部分，不是盖在屏幕上的。
- **引导的压暗**（`ONBOARD_DIM`）——它是把已有内容压暗，不是替换掉它。

需要"清空"一块区域时，正确做法是**不画那块区域的内容**，而不是画一块板把它盖住。开机自检就是这么做的：`BOOT` 阶段整个页面不渲染，因为终端确实还没启动完，本来就不该有卡片；自检文字于是直接落在空玻璃上。同理，引导要在状态栏写指引时，常驻读数**让位**而不是被覆盖。

## 配色

全部在 `client_ui/TerminalVisualTheme`。`ResourceContractTest` 钉住九个核心色必须在该类定义、且在终端屏幕里以 `TerminalVisualTheme.X` 的形式被引用。

> **`TerminalScreen` 顶部那 17 行 `import static` 不能删。** 契约断言的是源码文本里含 `TerminalVisualTheme.GREEN` 这样的子串，而 import 行本身就是唯一的匹配来源。IDE 的 "optimize imports" 会静默打断它。

### CRT 层

常驻叠加层由 `client_ui/TerminalChrome` 绘制，只覆盖 `DISPLAY`：

- **扫描线**：pitch 3、alpha 14、**纯黑压暗**、**绝对静止**。
- **暗角**：6 圈递减 alpha 的描边。

三条约束的来历：

1. **不得着色。** 早先有过一层 alpha-7 的纯绿叠加，它把整屏文字染绿、压掉对比度，已被删除并由契约测试禁止复活。压暗是中性的，着色不是。
2. **不得滚动。** 整块可读区上的移动高对比边缘是最可能触发光敏投诉的东西。滚动条纹属于天气工具天空监测仪的“损坏语言”，不属于常驻外壳。
3. **pitch 用 3 不用 2。** pitch 2 在这个 alpha 下会把像素字体的表观亮度削掉一半。

### 每帧开销

CRT 层与结构装饰合计约 105 个四边形/帧（扫描线 59 + 暗角 24 + 角标与标题栏约 20），相对重做前的约 120 大致翻倍，仍在一个 GUI 批次内。想再加一层时对着这个数字复核。

## 动画

时序常量与缓动曲线在 `terminal/TerminalMotion`（main 源集，纯类，`TerminalMotionTest` 直测）。运行时状态在 `client_ui/TerminalMotionState`。

### 时钟分工

| 用途 | 时钟 | 为什么 |
|---|---|---|
| 页面转场、标签指示条、按下反馈、卡片错峰淡入、开机自检打字机 | 毫秒时间戳线性 | 有确定起始瞬间；可被 JUnit 以“给定 t 返回什么”直接断言 |
| 平滑滚动、任务进度条 | 帧间 delta 指数 `1 - exp(-dt/τ)` | 目标会在飞行中反复改变（滚轮连打），重启式过渡会一顿一顿 |
| 脉动呼吸 | `renderAge`（tick） | 3 Hz 安全测试以 tick 推理 |

> **新代码不要用 `renderAge` 表示时长。** 它的整数部分被 tick 率钉死，服务器卡顿会直接改变动画速度。用 `render()` 里已经算好的毫秒时钟。

帧间 delta 钳在 100 ms，这样 alt-tab 回来不会一帧走完全程。

### 平滑滚动

四个滚动位置（记录 / 工具详情 / 文件列表 / 文件正文）的**整数字段保持权威**——它们同时是命中判定、钳制上限和契约断言点。平滑只是一层显示态：每帧向目标像素追赶，绘制时换算成首行索引加像素偏移，多画一行，外面套页面裁剪。

**命中判定不跟动画走。** 动画期间点到的是整数意义上的那一行，与松手后停住的位置一致；否则滚动中点击会打偏。

换页、重置文件视图、快照更新清缓存这三处必须直接吸附到位，否则新页会播放一段它从未有过的滚动。

## 首次开机引导

只在新档第一次打开终端时出现，**一次性、不可重看**。阶段策略在 `terminal/TerminalOnboardingPolicy`（main，纯类）。

| 阶段 | 推进条件 | 允许的输入 |
|---|---|---|
| `BOOT` | 自检播完（约 3.1 秒） | 全部吞掉；任意键把当前行一次打完 |
| `STEP_1`–`STEP_4` | 玩家点中当前目标标签 | 只放行目标标签与对应数字键 |
| `RELEASED` | 受伤兜底触发 | 全部恢复 |
| `DONE` | 第四步落地后再等 40 tick | 全部 |

步骤顺序是 **TOOLS → RECORDS → FILES → HOME**。终端开屏就停在 HOME，若让 HOME 打头，第一步会是一次同页点击——数据正确，但屏幕上什么都不会变，新玩家的第一个引导动作得到零视觉反馈。改序后每步都有真实转场，且末步把玩家送回任务卡所在的 HOME 页，正好在同一屏看到进度条走满、奖励到手。

### 与第一个任务的关系

引导的每一步走的都是**真实的翻页请求**，与玩家自己点标签走同一条服务端路径。四步走完，`learn_terminal` 自然满 4/4，奖励由服务端既有的完成路径发放。

**客户端没有任何一条能自行推进任务的口子**，也不写任何权威状态。这是刻意的：一个"我播完了"的信任口子会立刻变成刷奖励的入口。

### 完成停留（`COMPLETION_HOLD_TICKS`）

奖励与完成是同一个服务端 Tick，而带来这条消息的那份快照**已经在讲下一个任务了**。所以在加入停留之前，任务卡从来没有画出过任何一个已完成任务：玩家盯着的进度条被换成了一条他还没读过的新目标的空条，奖励却已经进了背包，屏幕上没有任何东西为它负责。第一项任务尤其明显——它在开机引导内部完成，玩家只是点了四个标签，就凭空多了 6 个面包。

判据是 `objectiveIndex` 变大。该序号只向前走，且只在某项任务的奖励**确实发放之后**才前进，所以序号增长等于服务端在说"你刚才看的那项已完成并已付款"。此时客户端把**上一份快照**的目标行（按 n/n 重写）、奖励物品与数量扣在卡上 60 tick（3 秒），期间：

- 卡片描边、进度条与奖励框统一走 `CLAIMABLE` 配色；
- 进度条补完最后一段而不是跳变——填满那一下正是停留要展示的东西；
- 目标行按 n/n 重写，右下角保留「任务完成」标签；
- 停留结束后进度条从 0 重新开始爬向新任务，而不是从满格往下掉——那两个数字属于不同目标，动画会画出一次并不存在的倒退。

3 秒长于引导自己的 40 tick 收尾提示，所以「引导完成」与卡上的完成态是同屏出现而不是先后出现。

**卡上不写「已发放 面包 ×6」这样的一行。** 同一件事这张卡已经说了四遍——目标行 n/n、进度条填满、整卡转完成配色、奖励框画着物品和数量——再补一句文字是卡片说完之后还在继续说。

同一件事在终端**关着**的时候由通知栈承担：`message.thefourthfrequency.task.completed_reward_claimed` 会连同任务名一起播报（「任务完成：认识终端 · 面包 ×6」）。任务名是独立的一组键 `terminal.thefourthfrequency.task.name.*`，不是目标行——目标行带着指令和计数，写在你正看着的卡上刚好，塞进物品栏上方那一行就过长了。`TerminalTaskService.taskName` 按 case 逐条写出这些键而不是按 id 拼装，理由与开机自检那六行相同：拼出来的键躲得过契约测试。通知栈在有界面打开时是**冻结**的，所以引导期间那条通知要等玩家关掉终端才浮出——这正是卡上停留必须存在的原因，而不是可以用通知替代的理由。

### 退出锁定

引导期间不能关闭终端。这是 [世界观圣经](world-bible.md) 里“退出路径”那条边界的唯一例外，它附带四个可测条件（一次性、有终点、有安全解除、服务端可越过），实现必须逐条对得上。

- 锁定期间关闭提示换成“当前无法退出”。**屏幕上写着“按 Esc 退出”而 Esc 无效是绝对不允许的。**
- 玩家一旦受到伤害立即解锁，进度保留。终端不暂停世界，"关不掉"在挨打时等于"打不还手"。
- 服务端强制关闭永远优先。
- 断线、重进、服务器重启后从当前步续上；只要点过任何一个标签，开机自检就不再重播。

### 每一步的简介

指针只说"点哪个标签"，那告诉新玩家把鼠标放在哪，没告诉他正在看的是什么。所以每一步在页面底部多一条**一行简介**，说明**当前显示的那一页**是干什么的，并以那一页的标签名开头。

简介主体（`onboarding.brief.*`）与包装（`onboarding.brief.current`，形如「当前页「主页」：…」）分开两个键，标签名直接取自标签条自己的 `tab.*`，所以简介开头写的名字与玩家眼前那个标签上印的字逐字一致。

| 当前页 | 简介 |
|---|---|
| 主页 | 当前目标、推荐工具与最近一条记录 |
| 工具 | 六件现场工具，随主线逐个解锁 |
| 记录 | 终端记下的事件，最新的排在最前 |
| 文件 | 回收到的文件，以及那本残缺的日记 |

**它描述当前页，不是箭头指向的那一页。** 早期版本讲的是箭头指向的页，结果同屏两行互相矛盾：状态栏写着「选择「工具」标签」，下面那行却像玩家已经在工具页一样介绍工具，而他眼前真正显示的主页反倒没人解释。选择哪一页由纯函数 `TerminalOnboardingPolicy.briefSubject(phase, currentPage)` 决定，直接单测。

改成讲当前页之后覆盖率不降反正好：终端开屏停在主页，步骤顺序是工具 → 记录 → 文件 → 主页，所以四步背后站着的页依次是主页、工具、记录、文件——四页各被介绍恰好一次。

位置是 `TerminalUiLayout.ONBOARD_BRIEF`，落在引导**已经压暗**的页面区内，**只在引导期间绘制**——所以它不占用平时的布局，也不可能和某一页自己的内容长期打架。

坚持一行是有意的：这是玩家一辈子只看一次的引导，同屏已经有四样东西在抢注意力；写成一段话没人会读，还会把指针挤出页面。长翻译按终端通用规则缩放，不截断。

### 高亮方式

压暗补集，不做全屏遮罩：把 `DISPLAY` 减去目标标签后的四条带压暗，**目标标签一个像素都不被盖**，它的背景、文字、未读闪烁全部照常。硬件列、状态栏和关闭提示区不压暗。

描边脉动用连续的升余弦，周期 2 秒（0.5 Hz），远低于 3 Hz 上限。连续函数没有“状态切换”可言，最短保持时长被平凡满足——但测试仍然断言相邻 tick 的差值有界，因为那才是“它确实连续、不是伪装成正弦的方波”的可测形式。

## 物品本体：3D 模型与手持动画

### 模型

终端是**一台固定的一体式厚重手持设备**。它不翻盖、不折叠、不展开、不滑动，也不发生任何机械形变。这是产品边界，不是建模上的省事：设备是一台封死的仪器，一旦它会开合，"这台机器在工作吗"就变成了玩家从铰链上读的信息，而不是从屏幕上读的。

- 六张 128×128 UV 图集 `textures/item/old_terminal_shell_0.png` … `_5.png`，由 `tools/generate_terminal_3d_assets.py` 生成。
- 六个物品模型 `models/item/old_terminal_held_0.json` … `_5.json`，每个带完整的八个 `display` 透视。
- Blockbench 可编辑源：`docs/art/terminal/old_terminal_shell.bbmodel`（几何 + form 0 图集）。

几何是 5 个 element：一块 14×7×2.5 的机身承载整张正面，加上四条凸出的黄铜边框（上下条 + 左右护角），含边框总尺寸 15×8×3。**六个形态的几何逐字节相同**，差别只在图集，契约测试直接比对 `elements` 的序列化结果。

正面是 2:1，和 512×256 的面板底图一致，CRT 占宽度约 62%——与 `TerminalUiLayout.DISPLAY` 在面板中的占比相同。这条比例是有契约测试守着的：早期一版把机身做成了近乎正方形，横向的 CRT 变成了竖屏，手里那台和打开后那块屏立刻不像同一台机器。图集用 128 而不是 64，也是因为在 64 下右侧硬件列只有 11 像素宽，示波器和罗盘分不出来。

正面排布严格对着 UI 与概念图 `docs/art/terminal/terminal_six_forms_full_controls_concept.png`：左侧一块大号内嵌 CRT；右侧自上而下是信号示波器、圆形罗盘、调谐滑杆、双行 LCD、底部关闭提示区；**示波器右侧另有一枚独立的小型琥珀色未读指示灯**。保留黑铸铁、磨损黄铜边角、四角螺丝，青色与红色阶段另有氧化裂纹沿边框爬行。

物品定义按 `minecraft:display_context` 分流：**背包格**走原有的平面图标 `old_terminal_0`–`old_terminal_5`，其余每个视角（第一人称、第三人称、地面、展示框、头顶）都走 3D 外壳。两条分支都从 `custom_model_data` 的**第 0 槽**取同样的 0–5，所以手里那台和背包里那张图不可能对不上形态。

平面图标留在背包里是有意的：它承载阶段与未读灯这两条信息，而一个斜着的盒子在物品格里比一张画好的图标更难辨认。

### 六形态

| Form | 阶段 | 未读灯 |
| ---: | --- | --- |
| 0 | 绿色普通 | 灭 |
| 1 | 绿色普通 | **亮** |
| 2 | 青色激活 | 灭 |
| 3 | 青色激活 | **亮** |
| 4 | 红色异常 | 灭 |
| 5 | 红色异常 | **亮** |

奇数形态就是它偶数邻居**点亮了指示灯**，别的一个像素都不许变。契约测试是逐像素比对的：0 与 1 的差异必须全部落在指示灯那 6×6 的窗口里，且必须非空。这条约束是灯的语义本身——玩家看见琥珀色亮起，知道那意味着"有东西在等你"，而不是"这台机器变了"。

映射仍是 `视觉阶段 × 2 + (attentionActive ? 1 : 0)`，写在 `custom_model_data` 第 0 槽，由 `TerminalData.applyAttentionProjection` 投影。

### 动画

状态机在 `client_ui/TerminalHandheldAnimator`，全部数值在纯类 `terminal/TerminalHandheldPose`（common source set，可直接单测）。

设备本体不产生任何开合动画。它是一台**厚重的双手仪器**：玩家用两只手捧着它，演出的是**摄像机凑近屏幕**。

1. **待机**：双手捧在视线下方，机身后仰约 25° 使屏幕朝上——玩家低头就能瞥一眼。低幅呼吸晃动，这是常驻画面，幅度必须小。
2. **打开**：右键 → 终端抬起、放大、转正到与摄像机平行，FOV 同时适度收窄 → 屏幕占满画面后才打开 `TerminalScreen`。
3. **关闭**：反向——UI 先消失，玩家看到举在眼前的终端，再平滑落回捧持位置。

**玩家在世界中的位置不动，第三人称摄像机也不动。** FOV 由 `GameRendererTerminalFovMixin` 在 `getFov` 返回处乘一个系数，只在第一人称生效、只在演出期间偏离 1、最大只收窄 12%。

演出接管的是 `ItemInHandRenderer.renderHandsWithItems` 整个第一人称通道，不是在原版单手姿态上加变换。所有位置都写成**摄像机空间的绝对坐标**，设备不挂在任何一条手臂上。这是尺寸能被控制住的前提：早期一版让设备跟着原版物品变换往近裁剪面推，放大到 2.5 倍，黄铜边框同时穿出画面四边并穿过手臂。

> **接管这个方法就必须自己冲刷。** 它末尾有两行：
>
> ```java
> this.minecraft.gameRenderer.getFeatureRenderDispatcher().renderAllFeatures();
> this.minecraft.renderBuffers().bufferSource().endBatch();
> ```
>
> 1.21 的渲染是两段式的：`renderItem` 只把节点**提交**给 `SubmitNodeCollector`，真正绘制发生在这次冲刷。取消整个方法就把冲刷一并取消了，提交的终端会滞留到**下一帧** `renderItemInHand` 开头那次冲刷，用的是那时的矩阵——**永远慢一帧，贴在上一帧的相机姿态上**。静止时看不出来，转头越快偏得越远，快速转视角时设备直接被甩出画面，停下又回到中间。这不是姿态的问题，姿态里根本没有视角这一项；是绘制被推迟到了另一个矩阵上下文。`terminal-3d` 客户端套件的四视角断言就是为这条回归留的。

#### 切入与切出的装备动画

装备高度仍然读原版自己的 `mainHandHeight`，所以在物品栏里选中终端时它照样从下方升入画面，切走时照样沉下去。这条是刻意保留的，但它和"不能反复播装备动画"直接冲突，冲突点在原版怎么判断"物品换了"：

`ItemInHandRenderer.tick` 调用 `shouldInstantlyReplaceVisibleItem`，后者比较两个物品堆的组件，只跳过那些声明了 `ignoreSwapAnimation` 的组件类型。**`custom_data` 和 `custom_model_data` 都没有声明。** 而终端两个都在改：前者每次同步都重写，后者在未读灯或视觉阶段变化时改。放着不管，一台开着的终端会每秒好几次从手里掉下去再爬回来，收到一条信号看上去就像玩家换了手持物品。

所以 mixin 额外钩了 `shouldInstantlyReplaceVisibleItem`：**终端换终端时立即替换、不播动画**，其余一律走原版。范围只有这一条——切到终端、切走终端、两个别的物品之间互换，全都保留原版的装备动画。

#### 尺寸是被画框卡死的，不是调出来的

`TerminalHandheldPose` 里 `OPEN_SCALE` 的上界由两项决定，两项都很容易漏：

- **收窄 FOV 会把画面里的一切放大。** 按未收窄的视野算出来的尺寸，画到屏幕上时大约超出 15%。
- **约束在宽边。** 设备宽高比 2:1，所以卡住它的是最窄窗口（4:3）的**宽度**，不是最宽窗口的高度。

当前值下设备约占 4:3 画面宽度的 92%、高度的 66%。单测直接按这个几何算并断言不越界。

#### 设备画得比手近

`BASE_Z = -0.45`，而原版手持物品在 -0.72。**第一人称的手是要跟世界深度缓冲比较的**——任何比它更近的表面都会把它吃掉，这就是原版里贴墙时手会陷进墙里的原因。原版能糊弄过去是因为手持物品又小又在画面角落；这台设备又大又居中，同一次遮挡会把它**整个**抹掉，抬头看一眼天花板就够了。把距离砍掉近一半，需要多近的表面才能遮住它也就大致减半。

视觉上完全不变：表观大小和屏幕位置都是"偏移 ÷ 深度"，所以拉近深度的同时，`REST_SCALE`、`OPEN_SCALE`、`REST_Y`、`OPEN_Y` 全部按同一系数缩了。

#### 手放在哪

手臂是**真人尺寸的几何体，必须留在原版自己的深度**（-0.72）——跟着设备拉近就会被放大成巨手。于是两者深度不同，而在透视下**同一个世界偏移在两个深度上落在画面的两个位置**。

所以手的位置不是直接拿设备的世界坐标，而是先算出设备的下边缘和侧壁**落在画面上的角度**，再换算成手臂那个深度上对应的世界偏移（`TerminalHandheldPose.screenAligned`）。直接把设备坐标交给手臂，结果就是手臂距离合理但在画面里的位置不对——看上去就是**手没抓在机器上**。

| 轴 | 依据 |
|---|---|
| Y | 设备下边缘的屏幕角度 → 手臂深度上的世界高度，再补上原版自带的下沉量 |
| Z | 固定在原版深度，不跟随设备 |
| X | 设备侧壁的屏幕角度 → 手臂深度上的世界横距，减去原版自带的手间距 |

还必须随 scale 变：设备从待机到打开会放大近一倍而手臂不会。固定偏移只在某一个 openness 上看着对，其余位置手会沿着机身向内滑——看上去像抓不住。

#### 转向惯性

原版在 `renderHandsWithItems` 里有一段：

```java
poseStack.mulPose(Axis.XP.rotationDegrees((getViewXRot(pt) - xBob) * 0.1F));
poseStack.mulPose(Axis.YP.rotationDegrees((getViewYRot(pt) - yBob) * 0.1F));
```

`xBob`/`yBob` 是平滑跟随的视角角度，差值就是头比手多转了多少，十分之一就是手该滞后的量。**接管整个方法会把它一并跳过**，必须自己重现——否则设备是刚性焊在镜头上的，转头时最先被玩家发现，因为它又大又居中。

#### 什么时候不接管

- **副手有东西**：两只手都占住终端就等于悄悄不画另一件物品——这也是原版对地图的规则。此时退回单手路径，只由 `renderItem` 钩子加一点倾斜与呼吸。
- **异象正在隐藏双手**：`ItemInHandRendererAnomalyMixin` 为脱离式第二人称镜头取消了这个方法，接管会把手又画回来。

第三人称与其余 display context 直接穿过去。

**不写物品堆，一个字节都不写。** 旧实现把帧号写在 `custom_model_data` 第 1 槽的客户端副本上；现在那个槽整个退役了。原版 `ItemInHandRenderer.tick` 一旦发现可见物品堆变了就会重播装备挥手动画，所以任何逐帧的组件写入都等于在整段演出里每秒重新装备几次终端。

**中止路径必须齐**：动画期间切换手持物品、死亡、切维度、断线或收到服务端关闭指令，都要立即复位并丢弃暂存的快照。另外，服务端在终端开着时大约每秒推一次快照——重复的快照只能更新暂存内容，绝不能重启开启动画，否则设备会永远停在半途而界面永远不出现。反向也要连续：开到一半按下关闭、或关到一半又打开，新阶段的起始时刻按当前 openness 回推，而不是从头再来。

## 未读指示灯

### 位置

`TerminalUiLayout.UNREAD_LAMP = (472, 46) – (488, 62)`，在**示波器右侧**腾出的那条带里。示波器右边界从 484 收到 468，把 16 像素让出来；`COMPASS`、`RECEIVER_SLIDER`、`RECEIVER_LCD`、`CLOSE_HINT` 一个像素都没动。

给它一块**自己的**区域，而不是从某个邻居身上借个角：硬件列上每一件仪器都已经在回答一个问题（北在哪、载波多强、接收机怎么想），在其中任何一件上叠第二层含义，都会让那件仪器恰好在最需要被信任的时候变得有歧义。测试断言的是强形式——灯与上述五个控件（含两条 LCD 文本行）逐一互不相交。

### 状态

灯的亮灭与物品六形态用**同一个** `attentionActive`，四个来源：

- 有未读信号；
- 有未读文件；
- 导航完成仍未确认；
- 有可领取任务奖励。

纯规则在 `TerminalAttentionPolicy.attentionActive(int, int, boolean, boolean)`；从记录里取字段的唯一入口是 `TerminalData.attentionActive(CompoundTag)`，物品投影和快照发送都走它。UI **不重写一套近似判断**——四个来源里"导航完成未确认"根本不在线上，任何用现有字段拼出来的近似都会和玩家手里的物品对不上。该布尔以 `attentionActive` 随主快照下发（v13）。

### 表现

- `attentionActive=false`：暗色灯罩 + 黄铜边框。灯罩是死的，但外壳还在，玩家知道这里有一个指示器。
- `attentionActive=true`：琥珀色核心点亮，缓慢轻微呼吸脉冲。
- **阶段变青或变红时，未读灯仍是琥珀色。** 它报告的是"有没有东西在等你"，阶段并不改变这个问题的答案；跟着阶段变色会让人以为它开始报告别的东西了。

脉冲是连续升余弦，周期 2.4 秒（0.42 Hz），是 3 Hz 上限的七分之一，强度在 0.55–1.0 之间，**永不熄灭到零**。不用闪烁：闪烁是眼睛读作"警报"的东西，而这盏灯只要有东西未读就可能亮一整局。曲线在 `TerminalUiLayout.unreadLampIntensity(double)`，接受小数 tick（调用方传的是 renderAge），测试按 0.05 tick 采样断言相邻差值有界——否则就是一个套着正弦名字的 20 Hz 阶梯。

绘制在 `client_ui/TerminalLampRenderer`，独立文件（见下面的技术债一节）。

## 已知技术债

`ResourceContractTest` 对 `TerminalScreen.java` 用的是**源码文本断言**（约 18 个被断言的字符串只存在于绘制方法体内），这实际上把它钉成了一个不能重构的两千行文件——任何把绘制搬进新文件的尝试都会让契约变红。

真正的解法是把这些断言换成行为测试（该类已经有约 50 个 `*ForTesting` 钩子可用），而不是靠挪代码绕过。在那之前，新增的绘制代码一律进新文件，现有绘制不动。
