# The World Interface finale

The current rule book for the End finale in `1.0.0-rc.1`: entry conditions, the collective ritual, the state machine, numbers, the eight actions, both endings and the F8 contract.

The old "seven minutes, 360 base health, hotbar shuffle, 768-block erosion" and the old Overworld altar are both retired and no longer apply.

## Before the finale

The terminal mainline must advance through the server's objectives:

1. Click the terminal's four top tabs to complete "learn the terminal"; the task advances immediately. On a new save the first terminal opening walks the player through those four steps (order: Tools → Records → Files → Home) along exactly the same server path as clicking the tabs manually, and the reward is still granted by the existing completion path; the client has no entry point that advances a task itself. Once the task completes, the client pins the just-completed entry on the home task card for three seconds (see "the completion hold" in [Terminal interface and handheld form](terminal-ui.md)); that is presentation only and writes no authoritative state.
2. Collect 12 of any log or plank, and 6 iron samples; rewards are granted on completion.
3. Enter the Nether, find a Nether fortress, obtain 8 blaze rods and return to the Overworld. "Find a Nether fortress" is judged by a per-second server poll: standing on a structure piece generated by the fortress itself counts as arrival, using the same test the navigation tool uses for "structure reached" rather than a radius around a locator point — a fortress is extended, and any single point plus radius either fires outside the building or fails to cover most of the interior. Blazes only spawn in fortresses, so reaching 8 blaze rods also backfills that milestone: neither legacy saves nor players who blundered into a fortress before checking the terminal get stuck on something they have already done.
4. Craft 4 eyes of ender.
5. Record 3 real eye-of-ender throws.
6. Personally experience at least one Corrector pursuit; capture and escape both count, only a technical interruption does not.
7. Find and approach the stronghold, then enter the End.
8. Defeat "The Fourth Frequency · World Interface".

Each completion advances to the next immediately; the item shown in the upper right goes into the inventory, or drops at the player's feet if there is no space.

After at least one personal pursuit, remaining unfinished pursuits are neither re-issued in the End nor allowed to block the finale; capture and escape both satisfy the threshold. Ordinary anomalies and real pursuits are paused during the End and World Interface pressure; the rules are in [Anomalies, terminal forms and personal pursuits](anomalies-and-pursuits.md).

Back up the save before inserting the last eye. The finale leaves permanent (though budgeted) scars in the End, and the ending also creates an isolation marker for the current local save.

## The native main island

- The fight happens on the native End main island; no large artificial platform is generated.
- An 11×11 altar, twenty inert gateways and ten authoritative stability anchors are placed flush with the ground.
- The altar centre and the vanilla return area have protection radii; bedrock, the obsidian pillars, End teleport structures, block entities, key mod blocks and the immunity tags are never rewritten by the fight.
- **The collapse-driven End erosion only affects end stone**, and server and client use the same rule. The client previously repainted every solid block in radius as missing textures, so the ten obsidian pillars, their bedrock caps and the altar all dissolved into the erosion — while what actually gets written into the world was only ever end stone. The pillars keep their own textures and stand on rotting ground, which is exactly their job: players navigate by them.
- The permanent scar budget is 8192 blocks total with at most 32 committed per tick (`WorldInterfacePolicy.MAX_PERMANENT_TERRAIN_EDITS` / `MAX_TERRAIN_EDITS_PER_TICK`). The laser warns 90 ticks ahead, and a single sweep queues at most 160 blocks of scorching.

## The terminal escrow ritual

The ritual is not a single-player button; it is a server-authoritative collective transaction:

1. The altar freezes every online non-spectator at that moment; the roster must be 1–8.
2. Each player on the roster must **hold** their own valid bound terminal and right-click the resonance core to insert it. Having it in the inventory does not count — the sacrifice must be an action, not a confirm button. Right-clicking empty-handed still opens the screen, for viewing the roster and others' progress.
3. Before everyone has submitted, a player may withdraw or cancel.
4. A roster change, an indeterminate state after a server reload, or any failed validation rolls back and returns terminals by ledger.
5. Escrow commits atomically, and summoning begins, only when every submission is valid.

Terminals are held by the system during the fight; success, failure and safe recovery all go through the recovery ledger, so no item can be duplicated or swallowed by an abnormal exit.

## The one-way lifecycle

`UNPREPARED` is the sentinel before the real finale. The ten stages after it advance one way by wire ID:

| Order | Stage | Meaning |
| ---: | --- | --- |
| 0 | `UNPREPARED` | Finale not yet prepared |
| 1 | `ARENA_READY` | The native main island arena is ready |
| 2 | `WAITING_TERMINALS` | Roster frozen, waiting for terminals |
| 3 | `SUMMONING` | Escrow committed, summoning begins |
| 4 | `PHASE_1` | First combat form, health `>70%` |
| 5 | `PHASE_2` | Second combat form, health `>35%` |
| 6 | `PHASE_3` | Third combat form, health `≤35%` |
| 7 | `SUCCESS_RESOLUTION` | Lethal damage before the timeout |
| 8 | `FAILURE_RESOLUTION` | Collapse reached 100% first |
| 9 | `PORTAL_OPEN` | The 3×3 return exit is open |
| 10 | `COMPLETE` | Poem/return confirmed |

Healing cannot make a combat form regress. The server judges collapse before lethal damage in the same tick, so a borderline moment resolves as failure.

**The body flies; the head reaches down to be hit.** The three forms' bodies hang with their lower edge at **8 / 14 / 18 blocks**, all outside melee height — that is the design, not a mistake: the World Interface is a storm, and it does not land. What a player can hit from the ground is the part it lowers.

The clearance was adjusted twice. First, forms 2 and 3 went up 4 blocks and form 1 went up 2 — not because "it should be higher" but because of the **head**: the central skull is 3.3 / 5.8 / 6.9 blocks wide across the three forms, with a jaw hanging beneath it, while clearance is expressed against the **body's lower edge**. At the old numbers the third form's jaw reached about 1 block below ground at its lowest during animation — structural sag grows with lost health, and head tracking and clips stack on top — so the player saw a head half-buried in end stone. Raising the whole thing carries the necks and skulls up with it, so `NECK_STRETCH` changed to `1.91 / 2.17 / 2.53` in step (**longer**, not shorter).

Then the whole thing came back down 2 blocks, spending exactly the margin the previous step bought: after the raise the head cleared the floor, but it had also retreated to the very limit of a swing and could not be reached in practice. The current margin is **the jaw sitting 1.69 / 1.12 / 0.72 blocks above the ground across the whole animation** — still no clipping, but that is now *the promise itself* rather than slack, and lowering it further requires measuring first. `WorldInterfaceAnatomyTest.theCentreHeadClearsTheFloorThroughTheWholeAnimation` sweeps the whole health range, two full drift cycles and both ends of the gaze range, measuring the **underside of the jaw** rather than the skull's hitbox.

Clearance is expressed as "player's feet to the **drawn** lower edge of the body", and the entity origin is derived as `combatHoverHeight = clearance − massBottomLift`. `massBottomLift` must be measured against the model's real lowest shell (`WorldInterfaceAnatomy.MASS_BOTTOM_UNITS`, read from the slab layout in `WorldInterfaceModel.createLayer`) and cannot be estimated as "core height minus body half-width" — that overestimates clearance by 5–6.5 blocks, all of which lands underground, leaving part of the body buried for the whole fight and the summon descent slamming into the floor.

**Attackable parts number 14 / 16 / 20**: the body, three heads, two hit segments per neck, and one segment per drawn tendril.

**Hitboxes are bound to the rig, not to "where the rig would be at rest".** Each tick `WorldInterfaceRig` poses the whole skeleton — bind pose, neck growth, thirty-seven keyframe clips, hover drift, head tracking, structural sag — the server places hitboxes from that, and the client drives `ModelPart` from **the same evaluation**. Clip data itself is in `WorldInterfaceClips` (common); the client no longer runs the vanilla animation system separately. Model and hitbox cannot compute separately, because there is only one formula.

- **Head and neck** are the main melee targets. Previously the hitboxes stood on the static bind pose while clips flung the central skull around — gaze lock 96°, sky-lance dip 58°, nearly 20 blocks in the third form — so a player swinging at the visible skull hit air. The same period had a coordinate error: the live model passes through `scale(-1,-1,1)` and a half turn while drawing, mapping the model's own -Z to the entity's forward direction, but the old formula flipped only Y and not Z, putting every head and neck hitbox **directly behind** the storm, off by nearly 20 blocks in the third form.
- The central skull's hitbox bottom sits at **about 1.44 / 0.78 / 0.43 blocks** above the ground across the three forms, well inside one swing (eye height 1.62 + 3 blocks of reach), so it can be hit reliably from the ground; the side heads are smaller and higher, and are mainly for ranged. This contract is stated in terms of the volume a player can really hit: `WorldInterfacePartEntity` gives each head a hitbox 45% wider than the drawn skull (`WorldInterfaceAnatomy.HEAD_HIT_SLACK`), and the geometry test therefore measures `headHitRadius` rather than making a promise stricter than the game itself from the bare skull.
- **The hitbox is aligned to the jaw, not the cranium.** `SKULL_CENTRE_Y_UNITS` was originally `-0.2` — the centre of the cranium cuboid — but the cranium is not the head: the same bone carries a jaw (starting at +3.4 and reaching 2.8 units deeper), so the drawn head runs to +6.2 while a cranium-aligned hitbox stopped at +5.55. **The whole misalignment was at the bottom**, which is exactly the end a player standing under the storm is swinging at: a jaw right in their face took no hits, while the air above the brow did. It is now anchored on the jaw (`+1.45`), with the hit slack widened from 25% to 45%, so the bottom edge reaches the jaw while the top still covers the brow. The pair of horns on top is **deliberately excluded**: they are thin spikes another five units up, and raising the cuboid by half for two spikes is not worth it.
- **The three heads no longer knot.** Model-space Y points down and the model faces its own -Z, so for a drooping, forward-leaning neck chain **both positive yaw and positive roll push it toward -X**. The old code wrote `side × angle`, which twisted the head mounted at +X across the centreline and the one at -X the other way: both side necks passed through the central neck. In the second form the two side skulls are only 0.63 model units apart while being 7.2 units wide themselves. Signed values now come from `WorldInterfaceAnatomy.mountYaw/mountRoll/neckYaw/neckRoll`, and all three chains splay outward.
- **All three heads keep watching the player it is hunting.** Each tick the server writes the target's bearing and pitch relative to the body's facing (aimed at the **eyes**, not the feet) into two synced fields (`GAZE_YAW / GAZE_PITCH` on `WorldInterfaceEntity`, radians, relative), and `WorldInterfaceRig.headGaze` adds them to the skeleton **after** the clip and procedural layers. The side heads follow at weight 0.72, with yaw and pitch each capped at **60°** — clamped, not wrapped, beyond that. Outside combat (descent, idle) the body does not turn, but the heads still follow the player.
  - **The pitch cap used to be why this feature did nothing.** It was 30°, and the geometry of this fight does not fit inside 30°: the body is only "body radius + 3 blocks" away horizontally while hanging 8–18 blocks up, so the player sits at roughly 50° or lower relative to the head — every frame was clamped, the head permanently pointed at empty space some distance in front of the player, and getting closer did not move it.
  - **The heads no longer teleport.** Gaze is a synced value that steps once per tick, and the server turns at most 9° per tick, so drawing it directly reads as "still for three frames, then a jump" — on a seven-block-wide skull that reads as teleporting. `WorldInterfaceEntity.renderGazeYaw/renderGazePitch` keep the previous tick's value and interpolate by `partialTick`, consistent with vanilla's treatment of every synced rotation. **Hitboxes deliberately do not interpolate**: `rigPose()` uses raw values at both ends, so one pose serves both. The at-most-one-tick lead the rendering gains displaces far less than the head hitbox's own slack.
  - **Why it does not knot**: 68% of the yaw lands on the skull itself and 32% on `neck_b`'s yaw, and both are rotations about the neck chain's **own axis** — rotating about a bone's hanging direction moves no joint below it, so it is only "the head turning", never the two skulls approaching each other. The only thing that really moves a skull is the 0.20-coefficient roll on `neck_b`, which buys the reading "the whole neck leans that way". `WorldInterfaceRigTest.theHeadsNeverKnotHoweverTheyAreLooking` sweeps the whole yaw/pitch range and several clips, backed by the same non-intersection contract as the rest pose, so that coefficient cannot be raised without turning the test red.
  - **Pitch is applied only to the skull**, not the neck: a neck that takes pitch pushes the head down with it, and the head was only just lifted out of the ground. Turning the face is *looking*; bending the neck is *changing posture*, and the latter belongs to the clips.
  - Synced rather than computed twice: the server places head hitboxes from one pose and the client draws the model from the same pose. If the client solved toward its own local camera, the drawn head and the hittable head would separate — which is precisely what binding hitboxes to the rig exists to prevent.
- **Tendril** hit columns cover the last drawn segment, not the whole strand. **They are no longer stretched to the ground**: the drawn tendrils actually end 4–7 blocks below the body, and in the third form remain about 10 blocks up, so the old hitbox pinning a column to the ground put a hittable volume in air where nothing was drawn. Tendrils are therefore no longer a ground melee target — ground melee hits the lowered central skull and its neck; tendrils go to ranged players and anyone standing higher than them. Making tendrils a melee target again requires **lengthening the model**, not letting the hitbox keep lying for it.

The collision box itself takes its height from the drawn body's **real vertical extent** (about 12 / 23 / 32 blocks) rather than assuming "as tall as it is wide" — the storm is a stack of slabs half again wider than it is tall, and a cube-shaped height would leave the visible upper third untouchable by ranged attacks. The **shrink sequence** during a form change (down to 28% at the morph midpoint) now also runs through `WorldInterfaceRig.renderScale`, so the hitboxes shrink with it rather than leaving a ring of empty hit volume around a shrunken body.

### The skyhold window: forms 2 and 3 leave every melee range

`WorldInterfaceSkyholdPolicy` is the single source of truth for this behaviour — a pure class with no persistence. Using combat time (`activeTicks`) as the clock, each **900-tick (45-second)** cycle ends with **260 ticks (13 seconds)** raised **26 blocks** above the combat station, with 50 ticks of smooth climb and descent at each end. It applies to forms 2 and 3; form 1 never rises.

- **The ceiling is design, not a comment.** Total raised time is **28.9%** of combat, of which the completely unreachable apex is 17.8% — both below the 40% hard ceiling. `WorldInterfaceSkyholdPolicyTest` measures the proportion tick by tick rather than dividing two constants, so changing the window's shape (two climbs per cycle, say) is caught too.
- **Only bow, crossbow and trident reach while raised**: the body's lower edge sits at 40 / 44 blocks, and head, neck and tendrils all move up with it.
- **It keeps attacking while raised, just with a different hand.** The schedule does not stall for altitude; the only excluded action is the **grab-and-throw** — it closes tendrils within 26 blocks, and at the ceiling the body is more than forty blocks off the arena, so that 2.5-second telegraph missed every single time. That is not a dodge the player earned, it is the schedule spending a slot on nothing, and in a window where only ranged answers exist that is the most expensive slot there is. The other seven work from altitude by construction: laser, breath bolt and sky lance all aim at the ground, the tendril lash commits to a point on the ground, and the two deprivations do not care where the body is. The rule is in `WorldInterfaceActionScheduler.canStartWhileAloft`.
- **It says something first.** The climb's first tick plays `world_interface_flight` with a low roar. What the player hears is "changing weapons", not "the boss got stuck ascending".
- A phase's tick 0 is always at the station, so neither a phase opening nor a form change landing starts out of reach.
- Vertical and horizontal speed are budgeted separately (`CLIMB_SPEED` 0.70, `CHASE_SPEED` 0.11 blocks/tick): the climb must complete inside its own 50 ticks, while the chase must be slow enough to be circled. One shared speed would send a 33-block-wide body sliding across the island at 11 blocks per second.

**Standoff distance is "no closer than this", not "always this far".** It used to be written as a **setpoint**: the instant the player ran toward the storm, the station retreated too, so how long closing the distance took was entirely up to the storm and the player never caught up. Now it only approaches when the distance is **greater** than the standoff, and once inside it stops moving horizontally and lets the player walk the rest — which is also what makes "the head reaches down to meet you" mean anything.

**Standoff is solved from the head, not the body** (`WorldInterfaceAnatomy.combatStandoff`). The old formula was "body radius + one swing", which put the body's **leading edge exactly 3 blocks from the player in all three forms** — a twenty-five-block-wide body hanging eighteen blocks up, with its front edge starting three blocks ahead of you, reads as standing on your head.

But what the player swings at is never the body; it is the central skull, and the head hangs in front of the body. So the distance that has to be right is "player to head hitbox", and everything else should be derived from it: `standoff = head reach + head hit radius + 1 block`.

That change alone was not enough: the old neck lean was only -0.16 / -0.12, so the central skull reached only 2.8 / 6.2 / 9.3 blocks forward while the body half-width is 3.3 / 8.1 / 12.4 — **the head did not clear the body's leading edge at all**. So "the nearest standoff at which it can be hit" was necessarily a standoff with the body overhead, and no standoff formula could rescue it: pushing the body back pushes the head back too. The neck lean therefore increased to **-0.34 / -0.29**, taking head reach to 4.6 / 9.7 / 14.0 blocks, and the third form finally clears the body's leading edge by 1.65 blocks.

Results (three forms in order):

| Quantity | Before | After |
|---|---|---|
| Body leading edge from player | 3.00 / 3.00 / 3.00 | **4.77 / 6.77 / 7.65** |
| Head hit face from player | 1.09 / 0.76 / 1.12 | **1.00 / 1.00 / 1.00** (by construction) |
| Head hitbox bottom above ground | 1.44 / 0.78 / 0.43 | 2.16 / 2.12 / 2.25 (still well inside a 4.5 swing) |

The increased lean also raised the jaw's ground clearance, so the whole-animation clearance assertion became looser rather than tighter.

**The summon descent stops higher.** The thirteen-second arrival used to end exactly on the first form's combat station, making the last thing that happens in the entrance "nothing" — the arrival shot and the combat shot were the same picture. It now stops **12 blocks** above the station (`SUMMON_ARRIVAL_LIFT`) and hangs there, and once combat starts the chase brings it down at 0.11 blocks/tick, so for the first few seconds the storm is **pressing down toward the player** rather than already being in place when discovered.

### Form changes are a real departure again

The morph for forms 2 and 3 is 80 ticks (4 seconds) and the body **leaves the arena**: 12 ticks crouching in place to gather, then an accelerating climb to **110 blocks** above the arena floor, the form change at the 40-tick apex (where players cannot see it), then 40 ticks of deceleration back down to the new form's station. Position is written by `snapTo` rather than given as velocity, so both ends are consistent and a mid-save restart resumes on its own clock.

This is an **explicit reversal of the trade** made by the old in-place morph. The argument for morphing in place was that for 4 seconds there is nothing in the arena to hit, which stops the fight. That cost is now paid again in exchange for something else: a 25-to-33-block-wide body cannot become another body in front of the player, and while the shrink sequence can hide the frame where the model swaps, it cannot hide "the silhouette you have been fighting for two minutes was substituted in place". Flying out and coming back makes the next form an **arrival** rather than a replacement. A shockwave ring is emitted on departure (`phaseChanged`) and again on the final tick of the landing, with an added roar — one world event at each end.

The morph landing point includes the skyhold lift in effect at the time, avoiding a "descend to station → immediately climb again" that reads as landing in the wrong place.

## Health and collapse

- Maximum health is `600 × (1 + 0.5 × (frozen roster - 1))`: 600 for one, +300 per additional player, 2700 at eight.
- The collapse cap is 12000 ticks — 10 minutes.
- Collapse advances as long as any frozen member is online, in any dimension, and pauses when all are offline.
- Breaking anchors does not affect the collapse timer: the timer is fixed and anchors change only the interface itself.
- **Arrows and tridents are resolved at 2.5× against the World Interface** (`WorldInterfacePolicy.arrowDamageMultiplier`), with the multiplier applied before the anchor damage-taken coefficient, so breaking anchors is worth just as much to an archer as to a melee player. This is not a bonus for ranged; it is correcting the price. The arena deliberately hangs the body 8 / 14 / 18 blocks up, `WorldInterfaceAnatomy` states outright that the body is "a target for ranged only", and all a ground player can swing at is the lowered central skull. Yet ranged was previously paid melee rates — a fully enchanted bow does roughly 9 points per second, while an eight-player roster with every anchor standing regenerates 5.4 per second, so most of a whole session of shooting only cancelled the healing. At 2.5× an arrow does about 20 points, clearly outrunning the regeneration without turning the health pool into a formality. The multiplier applies to **arrows and tridents** (`AbstractArrow`) and does not cover splash potions, fireworks and the like, which are neither aimed at the body nor short on damage.
- When the combat-phase timer enters its last 200 ticks (10 seconds), the client HUD adds a red pulse, an enlarged centred second count and a terminal tone tightening every second, so the same-tick "collapse first" adjudication is visible before it arrives.

## The stability anchor trade

Surviving anchors heal and reconstruct the World Interface's shell, lengthen its attack interval, and project a radius-8, height-unbounded stability zone at their base. Players inside take 20% less World Interface damage, and neither the interface's combat scorching nor the failure erosion can modify terrain inside it. A player-caused anchor break permanently changes this run's coefficients and extinguishes the matching zone; the World Interface cannot destroy an anchor itself.

Breaking anchors rewrites the interface's damage taken and attack frequency, and those numbers exist only on the server. Each time an anchor falls, the client HUD sweeps a roughly 60-tick golden wash across the boss bar and briefly replaces the anchor label with "reconstruction↓ / activity↑"; the footer anchor lamps keep reporting the remaining count.

The vanilla-trained "towers first" instinct still has a cost here, but the interaction no longer lies: the first positive-damage player attack on an anchor during combat destroys it immediately. The terminal explains the trade before entry, and the destruction broadcast and HUD confirm the change on hit. Zero-damage, non-player, spectator and non-combat-phase sources still cannot break an anchor.

### What an anchor looks like, and what happens when it breaks

An anchor is no longer a tagged end crystal but the mod's own entity: a four-way clamp about 1.75×2.75 blocks, with no head and no face. Four completely identical claw assemblies are distributed at 90°, each splaying up and outward through upper arm, square pivot, forearm, wrist pivot and a lower gripping foot before closing back down, clamping the single bedrock cap at the pillar top from four corners and wrapping down over its edge — it stands on vanilla terrain and carries no base or platform. The torso surrounds a platinum-white chest core; on top there is only an exposed relay core on a very thin shaft, with clear space around it, because the traction beam has to be able to leave through a full 360° horizontally and at large pitch angles. Four calibration petals sit below the relay core's equator and are disconnected from each other; they do not form a ring, cage, crown or upward-facing aperture. Emission is limited to the two cores and a very small amount of gold seams at the joints.

Breaking an anchor is an authoritative event; the destruction sequence is only its presentation. On the tick of the hit, the anchor leaves the survival bitmask, stops healing and stops projecting its stability field, and immediately loses collision. The remaining 16 ticks are geometry coming apart.

**It explodes first and is drawn back in afterwards.** The old sequence was inward from beginning to end, on the grounds that "the structure is being recalled, not blown up" — that reading is still its **ending**, but it turned the one thing the player has been working toward all fight into a lamp going out. The order now is:

1. The relay core detonates on the spot — `EXPLOSION_EMITTER` plus close-range explosion particles;
2. Three detonation rings step outward across the bedrock cap, each carrying outward velocity and continuing to expand after the wavefront is drawn;
3. The beam it has been holding is released and fires a vertical column of light — the same shape as the ten anchors igniting in sequence during the summon, closing the loop on "what were those ten columns for";
4. A radius-26 shockwave ring leaves the pillar base;
5. Two audio layers: the vanilla explosion (which every player reads as "that thing just came apart") over `world_interface_anchor`'s own voice, pitched down to 0.62;
6. The client's first two beats (fracture, beam retraction) now throw fragments **outward**, and only then rejoin the original inward implosion and violet embers. The per-anchor particle cap rose from 64 to 100 and the per-tick cap from 12 to 24; ten anchors together are still inside `StabilityAnchorGeometryTest`'s cap of 1024.

**The camera answers too.** The old implementation inferred it on the client from "the survival mask changed", using the lightest shake tier, originating at the **arena centre** with 96-block falloff — so a player standing next to the anchor they just broke felt it *less* than a bystander at the island's centre. The server now sends `WorldInterfaceBlastS2C` from the anchor's relay core at HEAVY tier with 80-block falloff: whoever did it feels it most.

The whole sequence never calls a world explosion, never rewrites blocks, never spawns fire or drops, and particles have both per-tick and whole-fight caps. Residual visuals on disconnect or restart are cleared outright and never resume across saves.

| Anchors broken | Damage taken | Cooldown coefficient | Total healing from survivors | Stability zones |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 60% | 1.15 | 0.20% max health per second | 10 |
| 5 | 80% | 1.00 | 0.10% max health per second | 5 |
| 10 | 100% | 0.85 | 0 | 0 |

Each broken anchor raises damage taken by 4 percentage points and stops one share of healing, while the cooldown coefficient drops 0.03 and the matching stability zone goes out. Base boss movement speed is fixed at 0.11 and no longer varies with anchors. So the reward for breaking anchors is **bringing the health pool down faster**, at the cost of denser attacks and less safe ground — rather than the previous perverse incentive where breaking more made it tankier.

Each surviving anchor restores 0.02% of the target's maximum health per second; all ten together make 0.20% per second. When entering the vanilla End poem on success, the server also submits the final broken-anchor count, and the client picks between "all preserved", "partially broken" and "all broken" success narratives accordingly.

| Tendril lash | 45-tick raise, then once every 45 ticks, three times (each with its own 32-tick wind-up) | Each strike targets **the nearest player not yet hit this round**, dealing 8 damage and knockback within 5 blocks while scorching the ground at the impact point with radius 3 capped at 12 blocks. Once all three have been used, it starts over, so a solo fight is exactly as before |
| Forced expulsion | 120-tick telegraph | With at least 3 players, selects `ceil(30%)` targets; never selects an integrated-server host; 3600-tick cooldown; **prefers players not yet expelled this fight**, only allowing repeats once everyone has been through a round |

**Later forms are more destructive.** The same action resolves damage at 1.00 / 1.15 / 1.30 in forms 1, 2 and 3 (`formDamage` = 1 + form × 0.15), impact scorching gains +1 radius and +50% cap, and the sky lance's effect radius scales by 1.00 / 1.22 / 1.44 (`formRadius` = 1 + form × 0.22). The damage step is deliberately smaller than the radius step: this attack goes through armour, resistance and Protection, so the gap between an unarmoured and a fully enchanted player is already close to an order of magnitude, and multiplying again per phase would only make the later forms feel arbitrary. The only two things that do not scale are the laser's burn radius and the tendril's lash radius: the former must stay smaller than the distance covered by the 10-tick tracking delay, the latter smaller than the distance a sprint can cover inside the telegraph. Enlarging them would not make the fight harder, only unreasonable in a way the player cannot see.

**Its roar is an ender dragon and a wither stacked.** `roar` emits `ENDER_DRAGON_GROWL` (pitched by form at 0.82 / 0.68 / 0.56) and `WITHER_AMBIENT` (a layer lower: 0.68 / 0.56 / 0.46 at 62% volume) at the same point on the same tick. Both are sounds the game has already taught the player, but on its own neither says the right thing: a dragon roar means "the End", but it says "that dragon", and this is not that dragon; the wither is vanilla's other boss throat, with a coarseness the dragon roar has none of. Stacked, and **pitched apart** (roughly a fourth), neither is itself any more — two samples at the same pitch just sound like one sample with chorus, and separating them makes it sound like one throat with two registers. Bigger forms are lower, so the same cue tells you from the far side of the island which body is out there.

**The schedule must exclude candidates with no available target before it picks one.** Inside the scan loop, "the grab cannot be used while aloft", "not enough players for a forced expulsion" and "this move currently has nobody to hit" are the same kind of judgement, and all of them must `continue` rather than being selected and then abandoned.

That rule was paid for by a real fault. The old code fixed the candidate first and only then asked who it could aim at; when the answer was "nobody" it simply returned. But the candidate is a pure function of `(phase, seed, index, previous action)`, and none of those four change while no attack is running — so the next tick made exactly the same choice and returned again, and the fight stood still until whatever made the target unselectable expired on its own. Three of the six actions unlocked in phase 2 are exclusive controls, each granting its target 600 ticks of immunity, and in a solo fight "the whole roster" is that one player: any selection landing on those three stopped the boss for up to 30 seconds, repeatedly. Phase 1 has no exclusive controls at all, which is why it only appeared after phase 2 — exactly where players reported it.

`WorldInterfaceActionSchedulerTest.everyPhaseKeepsAnActionThatNeedsNoExclusiveControl` guards the precondition that the scan always has a solution: no combat phase may unlock only exclusive controls.

**The three phases form a steep staircase.** Schedule intervals are **150–200 ticks** in phase 1, 75–105 in phase 2 and 35–60 in phase 3, and must be strictly monotonic (asserted by `WorldInterfaceActionSchedulerTest`). Phase 1 is deliberately slow: it is where a player meets all eight attacks for the first time, and a telegraph only teaches if there is quiet after it — at five to seven seconds the next lock opens while the last one is still being read. Phase 3 is continuous and additionally opens a **volley** channel alongside the schedule: several extra actions every 40 ticks. Volleys dispatch only the two actions the server draws itself — the breath bolt and the tendril lash — because the laser's and sky lance's geometry is solved on the client from the single action envelope, and a second copy would land where nobody can see it. Volleys write no save envelope, so they fall silent on restart along with cancelled scheduled actions, and therefore never touch the escrow ledger.

**Both the interval and the volley size tighten with the roster.** One attack points at one player, so a schedule written only against phase and anchor count gets divided by the roster: at an eight-player table each player is locked one eighth as often as in a solo fight, while the health pool grows only half a share per player — together, more players means everyone is idler, and the finale degrades from a fight everyone is in into a queue. The correction is in two places: the schedule interval is multiplied by `1 / (1 + 0.18 × (roster - 1))` with a floor of 0.45 (`rosterDensityMultiplier`), and each volley opens `1 + 0..1 + (roster-1)/3` actions with a concurrency cap of `3 + (roster-1)/2`. **In a solo fight both coefficients are exactly 1.0 and 3 — not one number changes** — and that is the configuration every other value in this fight was tuned against. Regardless of how the multipliers stack, the schedule interval may never fall below `MIN_SCALED_INTERVAL_TICKS = 20`: any faster and there is no quiet between two casts, and quiet is where the telegraph gets read.

Widening the volley is safer than compressing the interval, because it shortens no telegraph — it only makes more things happen at once; combined with the exclusion rules below, the extra slots land on players who are **not** being aimed at. Compressing the interval means everyone gets hit faster, so its coefficient is deliberately conservative.

## Multiplayer target allocation

The schedule and the volley are two independent channels. They used to pick targets separately with no knowledge of each other, so one player could be locked by the schedule and picked by three volley slots on the same tick — four telegraphs, one player, everyone else with nothing to do. Both channels now share one **attention ledger**:

- **No consecutive naming.** The player named last time is hard-excluded from the next selection as long as anyone else can be picked. This is stronger than the rule it replaced: the old `(seed ^ index) mod roster` was actually a perfect rotation when the roster was stable and its size a power of two, but the roster is rebuilt every time against exclusive-control immunity, death and arena radius, and one player entering or leaving shifts every index — measured over 600 attacks, the old rule produced runs of up to 10 on one player and a spread of nearly 50 between most and least targeted.
- **Recently targeted players are weighted lower.** The weight is `1 / (1 + hits within the window)`, with a 600-tick window (the same clock as exclusive-control immunity).
- **Volleys avoid whoever the schedule is currently locking**, and also whoever has already been assigned within the same volley; repeats are only allowed once candidates are exhausted — a rule that made a two-player table quieter than a solo one would be worse than nothing.
- **Roster-wide actions do not consume a slot.** The tendril lash names everyone by construction, and counting it into the ledger would raise everyone's weight at once, dilute the ledger's memory of who is actually being singled out, and immediately empty the volley's candidate pool, breaking the exclusion silently. The test is `singlesSomebodyOut`: it only counts as "targeting someone" when the target count is strictly less than the number of players present.

The ledger is **transient**, on the same trade as the volley channel: it decides only who is picked next, affects no damage, items or persistent state, and losing it degrades to uniform random rather than to something wrong. Persisting it would mean a schema version, a migration and a validation rule, at a cost out of proportion to the benefit; and a restart already cancels the current attack and grants a recovery grace period, so the fight forgetting who it was watching at that same moment is a promise it has already made.

The cost should be stated: in the ideal case of a stable roster whose size is a power of two, shares are no longer exactly even — across 600 attacks the most and least targeted differ by roughly a seventh to a fifth. That is intentional: a fight whose next target can be computed is a fight you can form up and wait for.

**The body's standoff follows the whole table, not the nearest player.** Position and facing use a `1 / (1 + distance)` weighted centroid (`WorldInterfacePolicy.attentionCentroid`); with one player the expression converges exactly to that player's own coordinates, so the existing tuning of standoff distance, hover height and turn rate is entirely unchanged. Vertical following still tracks only the nearest player — that rule was written for the spires and the anchors on them, and averaging one climber against three ground players serves neither. The previous hard "nearest" kept a body up to 33 blocks wide parked over one person for long stretches: blocking their view, burying the anchors and the core inside its silhouette, and — because the sky lance and the lash both hit the ground beneath the body — making standing closest mean standing where most attacks are going to land. The safest four-player strategy therefore became everyone backing off and letting one person absorb aggro they never asked for.

The three heads' **gaze** still follows the nearest player. That is the narrative expression of "it is looking at you", and the one piece of cheap personal targeting this change keeps.

Except for forced expulsion, every locking action gives three layers of telegraph during the lock: a full-screen border and countdown bar for the locked player, a tightening particle ring at their feet, and a **lock tone**. The lock window itself deals no damage — its whole purpose is to give the player time to judge.

**Only genuine locking actions use the lock tone** (`isTargetingLock`: laser sweep, breath bolt, sky lance, grab and throw, tendril lash). All five are **things flying at you carrying your coordinates**, the window exists so you are not where they are going, and their HUD copy is all "run / leave the impact point / open distance".

**Weapon impound and the gaze sweep are not locks.** They take something from you; there is nowhere to dodge to and the window is only a notice, and their copy says *what is about to be gone*, not *which way to go*. So they must never share the same warning: a missile lock tone promises "you still have time to get out", and spending it on something nobody can get out of teaches players to stop trusting it when it matters. Those two use the opposite shape — a `NOTE_BLOCK_BASS` low tone at a fixed 9-tick interval, pitch falling steadily from 0.95 to 0.55. It does not accelerate or converge, it only sinks: that reads as "something is being drawn out of you", not "something is on its way".

**The lock tone borrows the feel of a fighter being locked by a missile.** The search phase is sparse at an 11-tick interval, tightening to 3 ticks as the window advances, with pitch rising from 1.32 to 1.74 and volume from 0.26 to 0.42; past `LOCK_COMMIT_FRACTION` (70%) it becomes a fixed tone every 2 ticks (pitch 2.0, volume 0.52), an interval short enough to fuse into a **buzz** rather than fast beeping. The sample is `NOTE_BLOCK_BIT`, the closest thing vanilla has to a square-wave electronic tone.

The value of this shape is that **the rhythm itself carries the remaining time**: no attention needs to be allocated to it before it changes, and the switch to a fixed tone cannot be misheard. It solves a real problem — being locked used to be **silent**, and both the closing reticle and the countdown bar are in the centre of the screen, which only helps a player already staring at the centre of the screen; in a fight played by moving, that is exactly where they are not looking. A player reading the arena had no way to know they had been singled out other than being hit.

A UI sound is used deliberately rather than a positional one: a lock is not an event at some position in the world, it is a fact **about this player**, and it should neither attenuate with distance nor pan with facing.

**The progress bar only shows progress**: no tick marks, no threshold drawn on the bar. Lock completion is stated in words instead — the copy beneath the reticle becomes **`! LOCKED !`** in an emphasis colour the moment it crosses `LOCK_COMMIT_FRACTION` (70%). A line on a bar has to be learned before it means anything; a sentence does not.

That sentence only appears for genuine locking actions: impound and the sweep run on the same clock but nothing is being aimed, and their own copy ("held item about to be impounded" / "hotbar about to be cleared") is already the more useful line given there is no dodge.

### Every explosion shakes the camera

**The rule is: blasts are notified, beats are derived.** From the action envelope (id, start tick, duration, target) the client can work out which tick a given beat lands on, and those beats — the shell cracking during a form change, the summon's roar — stay derived on the client; sending an extra "shake now" packet only adds a less reliable clock.

Explosions are not that kind of event, and the old implementation treated them as one, wrong in three places:

- **The sky lance** shook on "lock + `SKY_LANCE_FALL_TICKS`", but that is a pure rendering constant describing the column's final 3 ticks of descent; the real impact is at "lock + the whole charge", i.e. **27 ticks (1.35 s) later**. The camera therefore answered a second and a half before the crater, reading as an unrelated tremor.
- **The tendril lash** shook every 30 ticks, while the three landings actually occur every 45 ticks after "raise + wind-up"; the two rhythms never lined up.
- **The third phase's volley channel** writes no action envelope at all, so an entire attack channel was silent on the camera — not mistuned, structurally impossible.

The server now sends `WorldInterfaceBlastS2C` where the explosion happens (coordinates + radius + tier, `LIGHT/MEDIUM/HEAVY/CATACLYSM`), and **the falloff is computed on the client**: the server knows where and how big, the client knows where its camera is, and one packet serves eight players in eight places. Players outside the radius get no packet at all.

| Source | Tier | Radius |
| --- | --- | --- |
| Laser impact (every 6 ticks) | MEDIUM | 42 |
| Sky lance landing | HEAVY | 72 |
| Breath bolt detonation | MEDIUM in form 1, HEAVY in forms 2–3 | Damage radius × 7 |
| Tendril landing | MEDIUM | 34 |
| Stability anchor destruction | HEAVY | 80 |
| Shockwave ring | HEAVY at radius ≥ 42, otherwise MEDIUM | Ring radius × 1.35 |

Shockwave rings are **deliberately capped at HEAVY**: the summon fires three rings within one second, and the client already has its own CATACLYSM-tier freeze-and-release near their landing points, so giving the rings the same tier would stack four peak impulses on one beat. The shake budget is a comfort limit, not a matter of taste.

The sky lance's **freeze frame** on the targeted player stays on the client (it needs to know "am I the target"); only the trigger tick changed from `+FALL_TICKS` to `+SKY_LANCE_CHARGE_TICKS`, matching the server's impact tick.

### The disappearing ability sounds after a long phase

On 2026-08-06 a server-side root cause was located and fixed: the attack schedule could stall on an exclusive-control action with no target. But a second reproduction on 2026-08-07 proved there was also a client-side problem: the server kept emitting attack and hurt sounds and the schedule was never overdue, and the client was still silent. Channel peak was only `16/247` at the time, and sliders and music gain were normal, so both channel exhaustion and the server stopping had already been ruled out.

The exact deadlock condition is the exclusive-control protection after phase 2: the old schedule fixed the action first and then checked whether it had an available target. While the only player in a solo fight was inside their 600-tick protection, none of the three exclusive controls could find a target; the old code returned without advancing the index, so the next tick chose the same action forever. Target eligibility is now a scan condition, unavailable actions are skipped, and any runtime with no persisted envelope goes through the normal cancel/recovery path before being rescheduled.

The hurt sound was a second, independent problem exposed at the same time. World Interface damage goes into a virtual-health transaction and never calls the vanilla hurt branch of `LivingEntity#hurtServer`, so merely declaring `getHurtSound()` plays nothing. Every transaction that successfully deducts virtual health now explicitly emits `world_interface_hurt` at the hit point, with a 4-tick perceptual throttle.

The client now watches the audio engine's own `gainBySource[HOSTILE]` rather than just the options slider; if that gain deviates from 1 during combat it is restored immediately and open sources are refreshed. The audio executor additionally reads each HOSTILE source's OpenAL state and calls `unpause()` only on sources genuinely stuck in `AL_PAUSED`; playing, stopped and not-yet-started sources are untouched. The log also counts the `world_interface_*` sounds the client actually resolves, the number of hurt sounds and the furthest source distance, so a future reproduction can separate gain/pause problems from network range/attenuation problems directly.

The three densest sources also keep rate limits; these are mixing-legibility protection and are no longer treated as the root cause of long-phase silence:

- Hurt sounds throttled to once per 4 ticks (at most 5 per second; particles and the screen flash are not throttled, so per-hit feedback is unaffected);
- Laser impact sound and shake moved to once per 6 ticks (terrain scorching still runs every 2 ticks, and the scorch line is continuous);
- The tendril wind-up tick moved from every 4 ticks to every 8 (the warning is carried by the ground marker; the tick only draws attention).

The throttle rule itself is the pure function `WorldInterfaceBlastService.permits(lastTick, now, minGap)`, covered by `WorldInterfaceBlastServiceTest` including "a save rollback that moves the clock backwards must not mute a source permanently".

> Note: automation can pin schedule invariants, damage transactions and sound resource contracts, but "still audible on every move after three continuous minutes" remains real-client manual acceptance.

### Mix headroom between the boss fight's sounds and its music

`AudioService.ENCOUNTER_MIX_TRIM = 0.72`, applied to **every** composed encounter cue: the server's `playBounded`, the client's `playBoundedLocal`, and the per-tick gain of the form ambience bed `AmbientLoop`.

Nowhere in the pipeline had the two been heard together: cues were tuned one at a time against silence, while the music was baked to a fraction of the master's gain before the game even started. The result was not "the fight is loud" but **"the music is gone"** — a dozen full-relative-volume cues over an already quiet track.

One coefficient rather than editing forty call sites: the cues' volumes **relative to each other** are composed and correct (a sky-lance impact *should* be louder than a lock tick). What is wrong is the whole group's position, and that is one number. Keeping it on a single constant also means "how loud is this fight" has exactly one place to answer it; `EncounterMixTrimTest` asserts all three mix points multiply by it.

**The only family it cannot reach is the borrowed vanilla one** (`playWithReach`: the dragon roar, the wither throat, the vanilla explosion). That method converts the radius it wants into the volume field — the only range control in the sound protocol — and any radius over 16 blocks needs volume > 1, which the engine **clamps to exactly 1** in gain terms. Those cues are therefore already at full gain, and multiplying by any coefficient would only shrink the radius, which is the very problem the method was written to fix. They are lowered by **reach** instead: `BLAST_REACH_BLOCKS` dropped from 96 to 72, and the engine's falloff is linear in radius, so across the forty-odd blocks this fight is actually watched from, explosions arrive at roughly three quarters of their previous level — level with everything else. Roars keep 96: a roar only the arena can hear is the original bug itself.

Grab-and-throw, impound, the sweep and forced expulsion are exclusive controls sharing one channel; a player has 600 ticks of protection after any exclusive control ends. The retired "grab and slam" left wire id 3 **permanently vacant rather than reassigned**: an encounter in an old save may still record that id, and silently reinterpreting a slam as a different attack is worse than failing to read it.

**Grab and throw names exactly one player.** It used to return two targets, of which only the first was ever actually grabbed, and the envelope was re-sorted by UUID before being sent — three consequences stacked: the higher UUID in any pair could never be grabbed; the second name absorbed 600 ticks of exclusive-control immunity for nothing, shrinking the candidate pool for later exclusive controls; and the client's lock presentation (post-process, lock tone, HUD, sky-lance freeze frame) is all driven by the same target list, so that player received a complete "you are locked" warning and then nothing happened. It was a remnant of the retired "grab and slam" and is now single-target like every other single-player exclusive control. Impounded weapons are still held by a persistent server ledger and returned exactly after a crash or reconnect; hotbar drops are not ledgered — dropped is dropped.

## The order of success resolution

Every beat of success resolution waits for the previous beat to **visibly end**; they do not overlap. Timing starts at `SUCCESS_RESOLUTION`:

The death clips divide the labour: `SUCCESS_COLLAPSE` handles the body and its ten tendrils — the body only drifts as it "stops holding itself level" (finally -22° pitch, 54° yaw), swelling to 1.14 before collapsing to 0.02; each tendril releases in turn at `1.9 + index × 0.36` seconds, tumbling 27 units outward and 17 units down as it shrinks away, **on the same schedule as the server's `emitLimbFailure`** — the burst has to land on the tendril that actually let go, or they are two unrelated things happening near each other. `SUCCESS_FADE` handles the lights and the ring, and the order is the meaning: the eyes flash once and go out (the *looking* stops before the thing on the field has come apart) → the jaw loses its support and opens → the ring goes last, the only part that turned continuously while it was alive, now leaving the body, rising 52 units, spinning to 2160° and dispersing.

This order has been changed twice. Originally the dragon spawned at tick 80 and gave thanks at tick 170, while the body was not removed until tick 260 — the thing the player had just killed was still hanging in the air collapsing while its replacement flew in to thank them for it; and the exit appeared out of the altar itself 90 ticks after the last line, unrelated to the dragon. The fix was to make the body leave first and the dragon arrive after, with the exit opened *by* the dragon, so "go back" is said to people who can already see the way out.

The third change was to the death itself, in two rounds. The first round's problem was that "death" existed only in the model — the body turned over, the eyes and ring shrank away, two 6-second clips — while **nothing at all** happened in the world beyond two sounds at the start: a thirty-three-block-wide body lay silently in the sky for 6 seconds and then ceased to exist between one frame and the next. The thing the whole mod leads to, and the arena said nothing about its death.

The second round changed what the death was saying. The body used to **fall** — turning over eighty-two degrees, tendrils flipping with it. Falling reads as "it was knocked down". But this ending is not about it being beaten, it is about it being ended; what it does as it leaves is **let go**. So it now rises, with only the drift of "no longer holding itself level" and no rotation, its components releasing one by one and falling, the whole body turning to ash, over a howl descending the whole way. Ash falls and the body rises; those two directions are separate — it is climbing, and the things it is made of are not going with it.

**The ender dragon leaves from the centre of the End, and no longer teleports or convulses.** Four things changed together, the first two on 2026-08-06 and the last two on 2026-08-07:

1. **The spawn point is the arena centre**, not a point on the orbit. It used to be placed directly on the radius-72 ring — while the summon sequence had just spent six seconds drawing everyone's eyes to the altar, so the dragon appeared seventy-two blocks away and the moment the ending most wants seen happened at the edge of vision. It is now added to the world inside the altar's column of light and spirals out onto the drawn ring over 70 ticks, closing the loop on "what was that circle of light for".
2. **The orbit angle became a cumulative quantity instead of being derived from the world clock.** The old expression was `(gameTime % period) / period`, i.e. `frac(gameTime / period)` — while `period` varies continuously from 600 to 190 during the descent. At a world time on the order of a hundred thousand, `gameTime / period` sweeps from about 167 revolutions to about 526 over the descent's 160 ticks, so **the fractional part cycles about 360 times — more than two revolutions per tick**. The dragon was thrown to an almost random point on the circle every tick, and `dragonApproach` happens to begin ramping **on the tick after the spawn**, so it was jumping from the moment it appeared. This was not a speed problem; that expression is simply not continuous in `period`.
3. **Vanilla's flight integration was removed from this dragon** (`EnderDragonMixin`). The server writes the dragon onto the orbit during `START_SERVER_TICK` — i.e. **before** the entity tick — and hands the step it just took to `setDeltaMovement` (which is its velocity anyway). But `EnderDragon#aiStep` ends with an unconditional `move(SELF, getDeltaMovement())`: once `HOVERING` has run through one server tick it always reports a flight target, and that branch is never skipped. **So every step was taken twice.** Let `d` be one tick of orbital displacement and `e` the body's deviation from the orbit at the end of that tick; the next server tick starts from the position vanilla left, giving `e = d - e_previous` — an expression that alternates between `d`, `0`, `d`, `0`. `d` is about 0.75 blocks on the high orbit and over 1.5 during the spiral exit; a body flung like that ten times a second is what the player saw as **convulsing**. The facing convulsed with it: it takes "the displacement actually travelled this tick", and every other tick that displacement is the difference of two nearly equal numbers, leaving the direction in the remaining noise. The fix redirects that one `move` away from this dragon; the rest of `aiStep` (wing beats, the flight history used by the neck and tail, part positioning) still runs. Not `setNoAi(true)`: in 1.21 that switch only stops the wing beats, and disabling the AI just gives a dragon with spread wings that does not move.
4. **Descent progress is no longer derived from the stage.** `dragonApproach` used to require the encoding still to be `SUCCESS_RESOLUTION` — and the tick the exit opens is exactly the tick that stage ends. So the approach fell from 1 to 0 between two ticks and the body was thrown from the low working circle at radius 17, height 15 straight back to the high orbit at radius 72, height 48 — **more than sixty blocks in one step**. That was the "it still teleports after spawning" teleport: not its entrance, its exit. The whole descent/return schedule now lives in `FriendlyDragonService.approach` and consumes only the dragon's own age, so no stage transition can push it, and the return became a real flight (`RETURN_TICKS = 200`).

Facing is also no longer given by a circular tangent formula but taken from **the displacement actually travelled this tick**: the path is no longer a pure circle (the radius spirals outward on exit and closes inward on the descent, with the height moving at the same time), and a tangent computed as if it were a circle points somewhere the dragon is not going. A displacement difference is naturally correct for any path. Vanilla's own turning does not compete: `aiStep` only changes yaw when the flight target differs horizontally by at least one hundred-thousandth of a block, and `configure` re-pins the target to the body's own position every tick, so that gate never opens.

`FriendlyDragonServiceTest` pins this down: it sweeps five descent durations and asserts that **displacement between adjacent ticks is always under 4 blocks** (the old expression could reach 144 in the worst case), with a separate source contract rejecting any return of the "world clock modulo period" shape. After fix 2 another case was added that flies the **real runtime schedule** — the original one scheduled the descent to begin only after the spiral exit finished, while at runtime the two overlap from tick 0, and it stopped at the end of the descent and never saw the tick the exit opens. The server test `friendlyDragonIsNotMovedByVanillaFlightIntegration` runs vanilla's `aiStep` directly after the server's own positioning and asserts that neither the body nor the yaw moved.

The second change was to the summon itself. After the body disappeared, only 20 ticks passed before the dragon was added to the world, with nothing in between and nothing announcing it: one tick an empty sky, the next a dragon already flying, seventy-two blocks away. So six seconds are now spent opening the sky — drawing the orbit it is about to fly in front of everyone, and only once it is drawn does it enter along that line. That also answers "where should I be looking": the time it takes the point of light to complete one circuit is enough for everyone to look up. The summon sequence **writes no save state**; it is derived entirely from the resolution clock, so a restart resumes at the current progress and a client joining midway can pick it up.

Failure resolution is unaffected and remains the full 260-tick escape sequence.

## The success exit and the poem

Once success or failure resolution completes, a 3×3 exit opens at the altar centre. Entering it follows the vanilla flow:

`showEndCredits → WinScreen → custom branch poem / credits / post-credits → PERFORM_RESPAWN`

The mod does not forge a second respawn system; the original spawn point is saved and restored by ledger. Only after the success poem is confirmed and the player is really back in the Overworld does the pre-ending per-dimension view distance of 6/12/16 (12 elsewhere) unlock to 16.

## The two endings and the local lock

### Success

- The World Interface is defeated before collapse reaches 100%.
- Terminal escrow, resource packs and window state are restored, the success poem, credits, post-credits and vanilla return complete; the success score is released before the resource packs are restored, so a reload does not restart it.
- A persistent success lock is created, and view distance unlocks once the player is actually back in the Overworld.
- The local successful save reads "sealed" and cannot be entered.

### Failure

- Collapse reaches 100% first, and the World Interface enters resolution/escape rather than remaining on the field as an ordinary boss.
- **The escape is an exit sequence**: the body hovers over the ruins it made for 30 ticks, then rises vertically — accelerating to 3.4 blocks per tick over 55 ticks with the core trailing particles, volume attenuating and pitch rising with altitude — so by the time the 170-tick resolution window ends and the projection is removed it is already hundreds of blocks up. It was not driven off and it is not hurt; it has simply stopped looking at this place. That is a worse reading than "freeze in place and vanish", and the correct one.
- Ordinary singleplayer or remote clients no longer close the game after the fixed Windows/fallback sequence: the vanilla return sends them to the Overworld, the client keeps running, and missing-texture rendering plus an action-bar line take over the ending.
- A published-LAN integrated-server host keeps their server running and returns to the Overworld; only their own client renders blocks, entities and fluids as missing textures, and LAN guests are unaffected.
- A failing player can return to the main menu from the pause menu; after a relaunch the Alpha presentation is retained until F8 recovery completes, and a pending Windows transaction does not retire Alpha early.
- The local failed save reads "corrupted" and cannot be entered.

Both endings disable Singleplayer, Multiplayer and Realms on the title screen; Options, Accessibility and Quit remain available.

From the start of success or failure resolution, ordinary anomalies, gap pressure, decay and personal pursuits close permanently and do not reappear in the `COMPLETE` stage after the return.

## F8 recovery and replaying

- With no ending lock, F8 does nothing and does not toggle meta.
- With an ending lock, F8 opens a confirmation whose wording matches the success/failure outcome. Confirming restores the desktop, Notepad, window, resource-pack and sequence state the mod owns, then closes normally.
- The Notepad text the failure sequence writes states this step itself: its second paragraph is "restart the game and press F8 to undo every change the mod made to this computer". That window opens at normal size rather than maximised, so it does not cover the failure wallpaper it is written on top of.
- If Wallpaper Engine (`wallpaper32.exe` / `wallpaper64.exe` only) is detected running when the failure sequence starts, `-control stop` pauses its playback so the failure wallpaper is actually visible; the executable path is written into the transaction manifest and `-control play` resumes playback during F8 recovery. The mod never terminates the process, and never starts a Wallpaper Engine the player had closed themselves; a failure at this step degrades to "the desktop stays as it was" and does not block the rest of the recovery.
- After the restart, only the exactly-matching local ending save gains the lossless `.thefourthfrequency-corrupted` marker; a recorded success shows "sealed", a recorded failure shows "corrupted", and neither can be entered.
- The mod does not modify `level.dat`, region files or player data. Replaying requires a new world.
- If an ending transaction is interrupted, launch once with `-Dthefourthfrequency.safeMode=true` to run the safe recovery.
